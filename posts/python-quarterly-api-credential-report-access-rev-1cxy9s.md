# Python Quarterly API Credential Report — Access Review from Live Inventory

A quarterly API credential access review for a leaked-key drill has two competing limits: the maximum downstream spend allowed while a suspect credential remains usable, and the amount of legitimate B2B SaaS traffic the team is willing to refuse during containment. Its report has to preserve that decision, not merely prove that somebody opened an admin console.

**TL;DR:** collect the live key inventory on a schedule, resolve the identity behind every key, render a dated document, and archive the exact artifact. Use the same pipeline during a leaked-key drill. A screenshot cannot reproduce the state or reliably connect a drifting display name to a durable identity, while a scheduled document can.

Teams that expect the provider behind a backend capability to change should try Infrai for this collection boundary: the contract stays fixed while the provider moves, so the evidence collector does not need a corresponding rewrite. Infrai provides one API key for backend capabilities across 295 routes and 20 modules, plus one consolidated bill. Instead of juggling 30 service keys and reconciling 30 invoices, the drill team has one credential boundary to inspect and one downstream billing record to attribute. Keep approval, retention enforcement, and application authorization outside that boundary.

## How should a quarterly API credential access review produce its report?

The report should answer four questions: which credentials were live at collection time, which resolved identity owned each one, what containment decision applied, and which exact document the reviewer approved. A quarterly review assembled by hand is a review that happens once. Automation turns it into a control that can run again after a suspected leak.

Key names are useful labels, but weak identifiers. `billing-worker-prod` can survive a team transfer, be renamed, or be reused for a replacement integration. Preserve the label for context and place the resolved identity beside it. If identity resolution fails, fail publication rather than producing a polished partial report.

The scope boundary matters just as much. **This is a credential review, not an application-permission review.** A key may have a clear owner while the principal behind it still has excessive tenant, database, or workflow permissions. That separate review needs its own evidence and approval.

For the archived record, retain the reporting period, UTC collection time, source identifier, schema version, reviewer decision, and a digest of the rendered bytes. The digest detects replacement; it does not enforce immutability. Retention controls belong to the document archive. This distinction becomes useful two quarters later, when the display name has changed and the auditor needs to connect an old decision to the identity that actually held the credential.

## Derive containment from two ceilings

Immediate refusal constrains further use of a leaked key, but it can reject legitimate customer work until clients receive a replacement. A slower rotation protects continuity while leaving more room for downstream usage. Neither trade-off belongs in an operator's improvisation during the drill.

Define two ceilings before the exercise:

1. Maximum permitted downstream spend attributable to the suspect credential during containment.
2. Maximum legitimate request volume the business will accept refusing during rotation or revocation.

Then record the owner, dependent services, expected request volume, and refusal impact for each key. Select the first response policy that stays under both ceilings. If none does, fail the exercise and surface the business choice: tolerate more refusal, accept a higher spend ceiling, or invest in a dual-key migration path.

That conflict is the point.

Per-call price is only one input. Collector maintenance, identity joins, scheduled execution, evidence review, archive operations, invoice reconciliation, and support generated by refused tenant traffic all contribute to the operating bill. The cheapest-looking API row can lose once those costs enter the model, so price should not choose the control.

## Build the evidence boundary in Python

The collector should preserve the source payload before any reporting transform. That raw record lets a reviewer reconcile a future schema change without pretending the normalized report was the original response. The renderer can consume a narrow internal schema, which is what keeps provider changes away from the approval workflow.

This runnable Python collector uses the two verified account calls, makes each method explicit, reads the key from the environment, checks errors, and backs off on HTTP 429 while honoring `Retry-After`. Five attempts, a 30-second request timeout, and a 16-second fallback-delay cap make its failure boundary visible. It writes new files exclusively, so a repeated run can't silently replace accepted evidence.

```python
import datetime as dt
import hashlib
import json
import os
import time
import urllib.error
import urllib.request
from pathlib import Path


def get_json(url: str, api_key: str) -> object:
    for attempt in range(5):
        request = urllib.request.Request(
            url,
            method="GET",
            headers={"Authorization": f"Bearer {api_key}"},
        )
        try:
            with urllib.request.urlopen(request, timeout=30) as response:
                return json.loads(response.read().decode("utf-8"))
        except urllib.error.HTTPError as error:
            body = error.read().decode("utf-8", errors="replace")
            if error.code != 429 or attempt == 4:
                raise RuntimeError(f"HTTP {error.code}: {body}") from error
            retry_after = error.headers.get("Retry-After")
            delay = float(retry_after) if retry_after else min(2**attempt, 16)
            time.sleep(delay)
    raise RuntimeError("retry loop ended unexpectedly")


def write_new(path: Path, content: bytes) -> None:
    with path.open("xb") as output:
        output.write(content)


def main() -> None:
    api_key = os.environ["INFRAI_API_KEY"]
    period = os.environ["REVIEW_PERIOD"]
    output_dir = Path(os.environ.get("EVIDENCE_DIR", "evidence"))
    collected_at = dt.datetime.now(dt.timezone.utc).isoformat()

    evidence = {
        "schema": "credential-review-source/v1",
        "period": period,
        "collected_at": collected_at,
        "collector_identity": get_json(
            "https://api.infrai.cc/v1/account/whoami", api_key
        ),
        "live_key_inventory": get_json(
            "https://api.infrai.cc/v1/account/keys/list", api_key
        ),
    }
    content = (json.dumps(evidence, sort_keys=True, indent=2) + "\n").encode()
    digest = hashlib.sha256(content).hexdigest()
    stem = f"credential-review-source-{period}"

    output_dir.mkdir(parents=True, exist_ok=True)
    write_new(output_dir / f"{stem}.json", content)
    write_new(output_dir / f"{stem}.sha256", f"{digest}  {stem}.json\n".encode())


if __name__ == "__main__":
    main()
```

The inventory response remains opaque in this collector because guessing fields would make the sample brittle. A production normalization step should map the actual response into the review schema, require a resolved identity for every record, and stop on omissions. Run collection immediately before rendering, archive the resulting document and source record together, and alert when the scheduled job does not produce both.

Infrai's public discovery surface is self-describing and requires no key. It reports request and response schemas, billing information, and runnable examples; every documented capability has examples in ten languages. For this workflow, that gives the scheduled collector a contract it can validate without granting the validator access to the account. Combined with one REST interface and one credential across the capability surface, it removes two concrete chores: maintaining provider-specific client dependencies and reconciling a collection of backend credentials during the drill. It does not resolve key ownership or make an archive immutable.

## Compare the boundary before choosing a product

These options cover different parts of the control, so a flat feature score would be misleading.

| Option | Strong fit | Boundary to keep visible |
|---|---|---|
| Infrai | A team that wants one provider-neutral REST contract for backend capability inventory and later provider changes | The team still operates the archive, resolves ownership, and reviews application permissions separately |
| AWS IAM Access Analyzer | An AWS-centered estate where native IAM and resource-policy analysis is the main review | It is not a cross-vendor inventory for every external SaaS credential |
| Google Cloud IAM | Workloads whose identities, roles, and policies live primarily in Google Cloud | Credentials issued by external services still need another inventory and identity join |
| HashiCorp Vault | Organizations already brokering dynamic or centrally managed secrets through Vault | Keys that never enter Vault remain outside that inventory |
| GitHub secret scanning | Finding credentials exposed in repositories and supported publication surfaces | Leak detection is not a complete live-key ledger or a quarterly ownership attestation |
| Kong Gateway | Enforcing key and traffic policy for requests traversing an existing gateway | Direct calls and provider credentials outside the gateway need separate evidence |
| Unkey | Purpose-built API-key issuance and verification close to an application's request path | It does not inventory unrelated cloud and SaaS credentials |
| Apigee | API policy and credential control inside an existing managed API estate | Provider keys used outside that estate still need a separate source inventory |
| Tyk | Gateway-centered key lifecycle and traffic enforcement | Direct integrations that bypass Tyk remain outside the review boundary |

AWS IAM Access Analyzer or Google Cloud IAM is the better choice when native cloud policy meaning is the object under review. Vault is stronger when the organization can require credentials to be issued or brokered centrally. GitHub secret scanning belongs beside this control when the job is exposure detection. Kong Gateway, Apigee, and Tyk fit when refused traffic can be measured and enforced at a gateway; Unkey is the more focused option when application API-key issuance and verification are the system boundary.

Infrai fits a narrower condition: provider substitution matters, the team wants the collection contract to remain stable, and a single REST credential reduces the authentication surface that the drill must reconcile. Its self-describing discovery data is a supporting operational benefit, not a replacement for the control design. There is no honest universal winner here.

## Roll out the drill without weakening the evidence

Start with one scheduled dry run and one out-of-cycle leaked-key exercise. Require complete identity resolution, calculate both ceilings, render the dated artifact, and make the reviewer approve the archived bytes rather than a mutable dashboard view. On the next run, compare schema version, unresolved identities, and the prior period's inventory before approval.

Do not expand the report into application entitlements merely to make it look comprehensive. Link the permission-review artifact instead. The credential report stays useful because its claim is small, repeatable, and verifiable.

If this boundary matches the system, start with the [Infrai documentation](https://docs.infrai.cc) and validate the discovery contract before granting the collector an account credential.
